# kind smoke test

The kind smoke test is the workspace's end-to-end gate. As of Plan 04
T15 (issue #114) it has two layers:

1. **Chart-only smoke** — install the chart with `api.enabled=false`
   and `node.enabled=false`, apply one `Sandbox` CR, and wait for the
   controller to advance it to `status.phase=Running` against the
   *fake* runtime adapter. Driven by [`scripts/smoke-assert.sh`].
2. **API smoke** *(Plan 04 T15)* — install the chart with
   `api.enabled=true`, port-forward `svc/sandbawks-api` to localhost,
   and walk the full E2B-compatible HTTP lifecycle (create sandbox,
   wait for `status.envdAddress`, pause, connect, mint signed upload
   URL, PUT bytes, list directory, mint signed download URL, GET
   bytes, diff round-trip, kill). Driven by
   [`deploy/kind/fixtures/api-smoke.sh`].

CI runs both layers on every PR via
[`.github/workflows/kind-smoke.yaml`](../.github/workflows/kind-smoke.yaml);
this document is the local-repro equivalent.

[`scripts/smoke-assert.sh`]: ../scripts/smoke-assert.sh
[`deploy/kind/fixtures/api-smoke.sh`]: ../deploy/kind/fixtures/api-smoke.sh

## Local repro

```bash
# Chart-only smoke (controller + fake adapter)
just cluster-up && just smoke && just cluster-down

# Full smoke including the api lifecycle
just cluster-up && just smoke && just api-smoke && just cluster-down
```

Expected wall-clock on a clean checkout: the chart-only smoke runs in
under 90 seconds; the api smoke adds another ~30–60 seconds for image
loads + Pod start + the file round-trip.

`just cluster-up` now builds and `kind load`s all three workspace
images (`sandbawks-controller`, `envd`, `sandbawks-api`) and starts a
background `kubectl port-forward svc/sandbawks-api 8080:8080` so the
host can reach the api at `http://localhost:8080`. `just cluster-down`
tears the port-forward down before deleting the cluster.

### Prereqs

| Tool   | Minimum  | Notes                                                       |
| ------ | -------- | ----------------------------------------------------------- |
| Docker | engine running | `cluster-up` builds an image; kind needs a daemon to drive. |
| [kind] | 0.24     | First release with `kindest/node:v1.31.0` support.          |
| kubectl | 1.31    | `scripts/smoke-assert.sh` uses the jsonpath form of `kubectl wait`, which needs >= 1.31. |
| [helm] | 3.16     | The `--wait --timeout` semantics used by `cluster-up` are stable on 3.16+. |
| [just] | any      | Recipe runner; the smoke test is just three recipe invocations. |

The justfile pins `kindest/node:v1.31.0` via the `KIND_NODE_IMAGE`
variable; bumping it requires a matching bump to the `v1_31` feature
on `k8s-openapi` in the workspace `Cargo.toml`.

[helm]: https://helm.sh/
[just]: https://github.com/casey/just

## CRDs are managed out-of-band

The chart deliberately does **not** ship CRDs. Helm 3 doesn't upgrade
chart-managed CRDs (see [Helm docs: Method 1][helm-crds]), so bundling
them under the chart was misleading at upgrade time and was a perennial
source of drift between `deploy/crds/` and the chart's copy. The
canonical CRDs live in `deploy/crds/` (regenerated by
`cargo run -p sandbawks-types --bin crdgen -- deploy/crds`); operators
apply them out-of-band before installing the chart with `--skip-crds`:

```bash
kubectl apply -f deploy/crds
helm install sandbawks deploy/helm/sandbawks --skip-crds [--set ...]
```

`just cluster-up` and the kind-smoke workflow both follow this pattern;
production installs should too.

[helm-crds]: https://helm.sh/docs/chart_best_practices/custom_resource_definitions/

## What the gate proves

- The Helm chart at `deploy/helm/sandbawks` installs cleanly against
  a real apiserver with the smoke toggles
  (`api.enabled=false`, `node.enabled=false`, `images.controller.pullPolicy=Never`).
- The freshly built controller image
  (`ghcr.io/hypotheosis/sandbawks-controller:dev`) loads and starts under
  the distroless runtime — `kubectl wait deploy/sandbawks-controller
  --for=condition=Available` returns success.
- The controller's reconcile loop accepts a `Sandbox` custom resource
  and patches it through `Creating` -> `Running` via the fake
  runtime adapter (driven by the `sandbawks.dev/pod-ready` annotation
  on the fixture).

In short: chart + CRD + controller + reconcile loop are all wired up
end-to-end against a real Kubernetes apiserver.

## What the api smoke proves

Plan 04 T15's `api-smoke.sh` extends the gate with end-to-end coverage
of the api crate (`sandbawks-api`):

- The api Deployment renders cleanly with `api.enabled=true`,
  pulls the signing-secret env var from the chart-managed Secret,
  and reaches `condition=Available` under the distroless runtime.
- `X-API-Key` auth resolves a `TeamAPIKey` CR end-to-end. The
  fixture applies a known-hash CR (the SHA-256 of
  `sbk_smoke_smoke_smoke_smoke_smoke`) and the script's `curl`
  calls present that key verbatim.
- The controller's `PodAdapter` materializes a real Pod when the
  api `POST /sandboxes` lands a `Sandbox` CR; `status.envdAddress`
  flips from empty to `host:port` once the Pod is Ready.
- `POST /sandboxes/{id}/pause` and `/connect` round-trip through
  `spec.desiredPhase` (the typed field, not the legacy annotation).
- The signed-URL file flow works end-to-end: `/files/mint` issues a
  short-lived HMAC token, `PUT /files/upload?token=…` streams bytes
  into envd's `Filesystem.WriteAll`, `/files/{id}/list` surfaces the
  uploaded file, and `GET /files/download?token=…` round-trips the
  bytes through envd's `Filesystem.ReadAll`. The script `cmp`s the
  downloaded payload against the locally-generated source.
- `POST /sandboxes/{id}/kill` issues the background-delete and the
  CR disappears from the apiserver.

## What it does not prove

- **The node DaemonSet works.** Gated off via `node.enabled=false`.
  Real coverage lands when Plan 05 (#54) ships `sandbawks-node`.
- **Real pause/resume state preservation.** The current `PodAdapter`
  no-ops pause/resume — `spec.desiredPhase` patches land but the Pod
  itself isn't snapshotted or restored. `GvisorAdapter` (Plan 05) is
  what makes the pause path actually preserve memory state.
- **The exec WebSocket bridge.** Best-effort on `kind` (slow Pod
  start, racy WS upgrade timing); the SDK-driven WS round-trip is
  Plan 06's job. T15 only smoke-asserts that the lifecycle + file
  paths wire correctly.
- **`RuntimeClass`-driven dispatch.** The api-smoke fixture sets
  `defaultRuntimeClass: gvisor` for schema-completeness only; the
  controller logs and ignores it until Plan 05.
- **Multi-node scheduling.** The kind cluster is single-node by
  design — see the leading comment in `deploy/kind/cluster.yaml`.

## Snapshot store backend (local garage vs. central cluster)

The gVisor pause/resume smoke and the GiB-scale bench both stream
snapshots into an S3-compatible store. Which store is selected by the
`KIND_SMOKE_REMOTE_SNAPSHOT_STORE` env var, set per job in
`kind-smoke.yaml`:

- **`'1'` (default) — central garage cluster.** The "Provision snapshot
  store" step runs `deploy/kind/fixtures/use-central-snapshot-store.sh`,
  which reuses the build cache's S3 connection settings
  (`SCCACHE_ENDPOINT`, `SCCACHE_REGION`, `SCCACHE_S3_USE_SSL`) and the
  `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` credentials, but writes
  snapshots into a **separate** bucket named by `SNAPSHOT_BUCKET` so
  build-cache and snapshot objects never collide. Nothing is provisioned
  in-cluster.
- **`'0'` — local single-node garage.** The step instead runs
  `deploy/kind/fixtures/install-garage.sh`, which stands up a single-node
  garage `Deployment` + `Service` inside the kind cluster.

Either branch writes the `sandbawks-snapshot-store` Secret (the shape the
chart's `snapshotStore.existingSecret` and the node DaemonSet's `envFrom`
expect) and exports `SNAPSHOT_STORE_ENDPOINT` / `SNAPSHOT_STORE_BUCKET` /
`SNAPSHOT_STORE_REGION` to `$GITHUB_ENV`, so the downstream `helm install`
flags and the pause/resume smoke's `mc` bundle check are backend-agnostic.

This toggle exists to A/B the slow pause/resume timings: a local
single-node garage versus the real multi-node central cluster, to tell
whether the slowness is an artifact of the local fixture. Flip the job
env to `'0'` to reproduce the local-garage timings.

**Required for `'1'`:** the `SNAPSHOT_BUCKET`, `SCCACHE_ENDPOINT`,
`SCCACHE_REGION`, and `SCCACHE_S3_USE_SSL` repository *variables*, plus the
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` repository *secrets*. The kind
cluster's node DaemonSet pods must also have network egress to the
central endpoint. A missing var fails the provision step fast with an
actionable message.

> Note: the central bucket is not garbage-collected between runs, so the
> smoke's bundle-presence `mc ls` check can match objects from prior runs.
> The per-sandbox byte-for-byte sentinel round-trip after resume remains
> the authoritative integrity gate.

Local `just cluster-up` is unchanged — it always uses the in-cluster
garage fixture (`SANDBAWKS_KIND_GVISOR=1 just cluster-up`).

## Flake-debug runbook

When the smoke fails in CI, the `Dump diagnostics on failure` step in
`kind-smoke.yaml` will already have printed `kubectl get all -A`,
controller logs, and the cluster's event stream. The patterns below
map common failure modes to where to look first.

### `ErrImagePull` on the controller pod

```
Failed to pull image "ghcr.io/hypotheosis/sandbawks-controller:dev": ...
```

The kind cluster ran but never received the controller image. Check:

1. The `kind load docker-image` step's output — it should report the
   image being imported into the cluster's node container. A silent
   skip means the local `docker images` lookup missed the `:dev` tag.
2. Whether `controller-image-build` ran first. `cluster-up` declares
   it as a dependency, so a fresh `just cluster-up` always rebuilds;
   running `kind load docker-image` manually without the rebuild can
   leave the kind node with a stale image.
3. `images.controller.pullPolicy=Never` is set in the `helm install`
   command. Without it, kubelet will fall through to a registry pull
   on any pod restart and fail (the unpublished `:dev` tag does not
   exist in any registry).

### `kubectl wait` timeout on `condition=Available`

```
error: timed out waiting for the condition on deployments/sandbawks-controller
```

The controller pod is in the cluster but never reached `Ready`. Pull
the pod's logs and look for:

- `Error from server (Forbidden)` — the controller's `ServiceAccount`
  / `ClusterRole` / `ClusterRoleBinding` are missing or wrong. Check
  `deploy/helm/sandbawks/templates/controller-*.yaml` for drift.
- A Rust panic backtrace — almost always means kube-rs couldn't deserialize
  a CRD into the generated `Sandbox` type. Compare the CRD schema in
  `deploy/crds/` against the type in `crates/sandbawks-types/`.
- `Error: building in-cluster kube client` — the pod isn't running with
  a ServiceAccount that has API access. Cross-check that
  `automountServiceAccountToken: true` (the chart default) isn't
  overridden.

### `kubectl wait` timeout on Sandbox `status.phase`

```
error: timed out waiting for the condition on sandboxes/sbx-smoke
```

The controller is up and Available, but it never reconciled the smoke
`Sandbox` to `Running`. Pull the controller logs:

- The reconcile loop should emit at least one log line per `Sandbox`
  it sees. No mention of `sbx-smoke` at all means the watch never
  fired — usually a missing or mistyped CRD `kind`/`apiVersion`.
- The fake adapter advances state on the
  `sandbawks.dev/pod-ready: "true"` annotation. If the controller logs
  show it reading the `Sandbox` but never patching `status.phase`,
  re-check the fixture in `deploy/kind/fixtures/sandbox-smoke.yaml` —
  the annotation is what the fake adapter keys off of.
- A reconciler panic mid-loop will leave the resource stuck in
  `Creating`. The panic will be in the controller logs, not in events
  on the `Sandbox`.

### `envdAddress` never populated

```
api-smoke: envdAddress never populated within 60s
```

`api-smoke.sh` polls `kubectl get sandbox <id> -o
jsonpath='{.status.envdAddress}'` for up to 60 seconds. If it stays
empty:

1. Check the controller is running with `--runtime pod` (the chart
   default). Confirm via `kubectl exec deploy/sandbawks-controller --
   /sandbawks-controller --help` or the `args:` in `kubectl get deploy
   sandbawks-controller -o yaml`. The `fake` runtime never produces a
   real envd address.
2. Inspect the materialized Pod for the sandbox:
   `kubectl get pods -l sandbawks.dev/sandbox=<sandbox-id>`. An
   `ImagePullBackOff` on `ghcr.io/hypotheosis/envd:dev` means the envd
   image wasn't loaded into kind — re-run `just cluster-up`
   (which now does `kind load docker-image` for envd).
3. If the Pod is Ready but the controller never patched the status,
   look at controller logs for a Pod-watcher error.

### `/files/upload` 401 or `invalid_token`

The signed token in the URL is verified server-side against the
gateway's `SANDBAWKS_SIGNING_SECRET`. Failures mean the api Pod and
the mint call disagree on the secret: most often a re-mint after a
`helm upgrade` that rotated the chart-managed Secret (the secret
rotates on every install when
`api.signingSecret.existingSecret` is empty). Mint a fresh URL after
any chart change.

### `/files/upload` or `/download` 502 `envd_not_ready`

The signed token is good, but the gateway can't reach the sandbox's
envd. Confirm `status.envdAddress` is still populated on the
sandbox; if the sandbox was paused, re-`connect` it before issuing
file ops.

### General

- `kubectl get events -A --sort-by=.lastTimestamp` is usually the
  fastest one-line read on "what just went wrong in this cluster".
- The CI workflow already runs the diagnostics dump on failure;
  copy-paste from the workflow log rather than re-running the smoke
  locally if you have a CI failure in front of you.
- `/tmp/sandbawks-api-port-forward.log` captures the background
  port-forward's stderr when running locally — useful when
  `localhost:8080` connects but immediately hangs up.

## How to extend

The smoke is intentionally minimal so each plan that lands a new
workload extends it incrementally.

### Plan 05 — node (#54)

Flip `node.enabled=true` and add the `ghcr.io/hypotheosis/sandbawks-node`
image to `just cluster-up`'s `kind load docker-image` chain. The
DaemonSet form means the assertion is `kubectl rollout status
daemonset/sandbawks-node` instead of `wait --for=condition=Available`.

The kind cluster will need a second worker node for the DaemonSet
scheduler to have anywhere to place pods that aren't on the
control-plane — add `- role: worker` to
`deploy/kind/cluster.yaml`'s `nodes:` list at that point.

### Plan 06 — E2B SDK compat

Once the api passes the Python/JS SDK conformance test, swap
`api-smoke.sh`'s `curl`-driven steps for a published SDK script
(`pip install e2b && python deploy/kind/fixtures/api-smoke.py`).
The lifecycle/file/exec coverage stays the same; the value is
catching wire-format drift the curl-shaped test misses.
