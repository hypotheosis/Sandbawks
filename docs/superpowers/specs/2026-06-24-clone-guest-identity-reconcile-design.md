# Clone guest-identity reconciliation (snapshot-mode)

**Status:** Approved (design); implementation staged
**Date:** 2026-06-24
**Author:** Peter Grace (with Claude)
**Relates to:** #643 (this issue), #416 / PR #642 (`spec.restoreFrom`, clone-from-snapshot), #545 (runsc-version restore gate), #237 (mounts-lost-on-restore invariant), #603 (filesystem-mode persistence)

## Problem

A gVisor `snapshot`-mode restore reconstructs the entire Sentry (guest kernel)
from the source's checkpoint, so a **clone inherits the source's in-kernel
identity**:

- `gethostname(2)` / `uname -n` (UTS namespace) → the source's hostname.
- netstack interface MAC + assigned IP → the source's.
- any captured `/etc/machine-id`, D-Bus machine-id, boot-id (in the overlay,
  captured in `pages.img`) → the source's.

Meanwhile the kubelet-managed furniture binds (`/etc/hostname`, `/etc/hosts`,
`/etc/resolv.conf`) are **not** captured — they are gofer-backed host passthrough
re-materialized on the new Pod (see `RUNTIME_MANAGED_BIND_DESTS` in
`crates/sandbawks-node/src/gvisor.rs`) — so they reflect the **destination** Pod.

Net effect for a clone: a split between the kernel hostname (source) and
`/etc/hostname` (destination), plus a machine-id / MAC duplicated across the
source and every clone of it.

### Why this is a follow-up, not a restore blocker

- It does **not** fail the restore. The same-sandbox resume path already restores
  into a fresh Pod with a different CNI IP / veth MAC and works end to end, so
  gVisor tolerates a restore-time environment that differs from checkpoint time.
  The only hard restore gates are runsc-version (#545) and mount-set (#237).
- For a normal same-sandbox resume the Pod name equals the sandbox name, so the
  checkpointed hostname already matches the new Pod and the split is invisible.
  The mismatch is **specific to clone** (destination ≠ source).
- v1 cannot produce a live *collision*: a clone source is always quiescent
  (`Paused` / `Failed` for snapshot, `Suspended` for filesystem), so two
  identical identities are never on the wire at once.

The risk is workload semantics: software that keys on hostname / machine-id / MAC
(service registration, clustering, licensing, anything assuming a unique boot)
inherits the source's identity instead of a unique one.

## Scope of the decision

This issue is **snapshot-mode clones only**. A *filesystem*-mode clone (#603)
cold-boots a fresh Pod over CSI-cloned volumes, so its kernel identity (hostname,
machine-id, MAC) is freshly generated by the new boot — the only thing that
carries over is on-disk state, which is the workload's own concern. There is
nothing to reconcile at the runtime layer for filesystem clones.

## Decision

Adopt a **hybrid** strategy, evaluated against the four options in #643:

| Facet | Option | Decision |
|-------|--------|----------|
| UTS hostname (`uname -n`) | (2) post-restore rewrite | **Rewrite** to the new sandbox name, in-guest via `envd`. |
| `/etc/machine-id`, D-Bus machine-id, boot-id | (3) regenerate | **Regenerate** (blank `/etc/machine-id` so it is re-seeded; refresh D-Bus id) in-guest via `envd`. |
| netstack MAC / IP | (4) confirm + assess | **Accept** (no-op). |
| Overall posture | (1) document-only | **Rejected** as the *sole* answer — but the doc block stays, narrowed to the residual (MAC) and pointing here. |

### Rationale per facet

**Hostname — rewrite.** This is the most visible split (`uname -n` ≠
`/etc/hostname`) and the cheapest to fix. The UTS value lives in the checkpoint,
so there is no `runsc restore` flag that overrides it; the rewrite must happen
*in-guest* after restore. `envd` is already the first thing the restored Sentry
runs to working order (it is the entrypoint and survives the checkpoint, per the
#265/#270/capture-in-checkpoint work), so it is the natural actor: a
`sethostname(2)` to the new sandbox name brings `uname -n` back in line with the
kubelet-materialized `/etc/hostname`.

**machine-id / boot-id — regenerate.** A duplicated `/etc/machine-id` across
clones is the facet most likely to break real workloads (systemd journald keys,
D-Bus, licensing dongles, clustering membership). The conventional reset is the
"golden image" recipe: truncate `/etc/machine-id` to empty (and remove
`/var/lib/dbus/machine-id` if it is a regular file rather than a symlink) so the
next consumer re-seeds a fresh random id. `envd` performs this once on a clone's
first boot, before handing control to the workload. boot-id (`/proc/sys/kernel/
random/boot_id`) is kernel-synthesised and not separately persisted, so it
follows from the Sentry's own state and needs no explicit action beyond noting it.

**netstack MAC / IP — accept.** The restored netstack retains the checkpoint's
interface MAC/IP, but this is **not observable as identity on the wire**: the
sandbox's real L2/L3 identity is the host veth + CNI-assigned address on the new
Pod, which is freshly allocated. The in-guest netstack MAC is cosmetic — it never
leaves the Sentry. Rewriting it would mean reaching into netstack state with no
workload-visible benefit and real risk of destabilising the restored network
stack, which already tolerates a changed restore-time environment (that is
precisely why same-sandbox resume works across nodes). We accept it and document
the residual.

## Mechanism

A controller→Pod→`envd` one-shot, riding the existing restore flow with no new
control-plane round trips:

1. **Classify (pure, types crate).**
   `sandbawks_types::sandbox::clone_needs_guest_identity_reset(restore_from,
   effective_mode)` returns `true` iff `restore_from` is set **and** the resolved
   persistence mode is `Snapshot`. This is the single source of truth both the
   pod-materializing edge and any future caller branch on.

2. **Mark (controller, pod_adapter).** When the predicate holds, the controller
   stamps the restore Pod with the annotation
   `sandbawks.dev/clone-identity-reset: "true"`
   (`CLONE_IDENTITY_RESET_ANNOTATION` / `CLONE_IDENTITY_RESET_VALUE`). It is an
   *annotation*, not a label: nothing schedules or selects on it; it is a one-shot
   instruction consumed once per clone boot. The new sandbox name is already
   available to the guest as the Pod hostname / `/etc/hostname`, so the reset
   target needs no extra plumbing.

3. **Reset (`envd`, first boot).** On startup `envd` reads the annotation from its
   downward-API projection. When present and unconsumed, it runs the one-shot
   reset *before* serving the workload:
   - `sethostname(2)` to the new sandbox name (read from `/etc/hostname`, which
     the kubelet has already materialised to the destination Pod's value);
   - truncate `/etc/machine-id`; drop a non-symlink `/var/lib/dbus/machine-id`;
   - record that the reset ran (idempotency marker under `envd`'s run dir) so a
     *subsequent* same-sandbox resume of the clone does not re-reset — by then the
     clone *is* the legitimate owner of its (now-unique) identity.

The annotation is absent on cold boots, on filesystem-mode clones, and on
pre-#643 clones; every consumer treats a missing value as "no reset needed".

## What lands in this PR vs. follow-up

This PR delivers the **decision and the first load-bearing contract**, unit-tested
without a cluster:

- the design decision recorded here (the primary #643 acceptance criterion);
- the pure predicate `clone_needs_guest_identity_reset` in `sandbawks-types`,
  with tests pinning the snapshot-clone-only semantics;
- the cross-crate annotation contract (`CLONE_IDENTITY_RESET_ANNOTATION` /
  `CLONE_IDENTITY_RESET_VALUE`), documented as the controller→`envd` seam;
- the narrowed doc block on `SandboxSpec::restore_from` pointing here.

The **runtime wiring** — controller stamping the annotation at pod materialization
and `envd` performing the in-guest reset — is deliberately *not* in this PR,
because its acceptance test is intrinsically a live-cluster e2e
(`kubectl exec` against a running clone, per #643's verification block) and cannot
be validated in the current headless/no-cluster sandbox. Landing the contract now
lets the controller and `envd` changes be reviewed against a fixed seam, and keeps
this PR's claims honestly limited to what its tests actually prove.

## Acceptance mapping

- **"A documented decision on the strategy (even if accept+document wins)."** —
  Satisfied by this spec: hybrid (rewrite hostname + regenerate machine-id, accept
  MAC).
- **"If we rewrite identity: a clone reports its own hostname via both `uname -n`
  and `/etc/hostname`, and a unique machine-id, verified by an e2e test."** — The
  mechanism above produces exactly this. The e2e test
  (`kubectl exec <B> -- sh -c 'uname -n; cat /etc/machine-id'`, asserting
  `uname -n == B` and `machine-id != A`'s) lands with the runtime-wiring follow-up,
  since it requires a live cluster the contract-only PR cannot exercise.

## Verification of current behavior (to confirm against a cluster)

```bash
# source A, before pause:
kubectl exec <A> -- sh -c 'uname -n; cat /etc/hostname; cat /etc/machine-id'
# clone B from A, once Running:
kubectl exec <B> -- sh -c 'uname -n; cat /etc/hostname; cat /etc/machine-id'
# expectation per analysis (pre-fix): B's `uname -n` and machine-id == A's;
# B's /etc/hostname == B.
# expectation post-fix: B's `uname -n` == B, /etc/hostname == B, machine-id != A's.
```
