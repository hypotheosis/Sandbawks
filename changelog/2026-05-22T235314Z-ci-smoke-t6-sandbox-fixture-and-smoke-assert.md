# CI smoke T6 — Sandbox CR fixture + kubectl smoke assertions

**Issue:** #72
**Epic:** #66 — CI: kind-based deployment smoke test
**Date:** 2026-05-22

## What landed

- `deploy/kind/fixtures/sandbox-smoke.yaml` — a `SandboxTemplate`
  (`smoke-template`) plus a `Sandbox` (`sbx-smoke`) in the `default`
  namespace. The `Sandbox` carries the `sandbawks.io/pod-ready: "true"`
  annotation so the Plan-02 reconcile loop will advance it from
  `Creating` to `Running` against the fake adapter without needing a
  real backing pod.
- `scripts/smoke-assert.sh` (executable) — waits for
  `deploy/sandbawks-controller` to reach `Available`, applies the
  fixture, then waits up to 60s for `sandbox/sbx-smoke` to reach
  `status.phase=Running` using the jsonpath form of `kubectl wait`
  (which requires kubectl ≥ 1.31, matching `KIND_NODE_IMAGE`).
- `justfile` addition: `just smoke` — thin wrapper over
  `bash scripts/smoke-assert.sh`. Chained after `just cluster-up` in
  the (forthcoming) CI smoke job.

## Why these choices

### `sandbawks.io/pod-ready` annotation lives in the fixture

`crates/sandbawks-controller/src/reconcile.rs::derive_trigger` only
returns `Trigger::PodReady` when the Sandbox has
`sandbawks.io/pod-ready: "true"` set. Plan 03 will replace that
annotation with a real pod-watcher signal, but Plan 02 (the controller
this smoke test exercises) reads it directly. Setting the annotation
at apply-time is the minimal way to drive the happy-path transition
without standing up an actual pod — and it matches the contract the
existing unit tests in `crates/sandbawks-controller/tests/reconcile.rs`
already rely on.

### Fixture schema matches the *generated* CRDs, not the issue text

The issue body's YAML used `defaultTimeout: "60s"` /
`timeout: "60s"` (strings). The actual CRDs generated by `crdgen` from
`sandbawks-types` use **integer-seconds** fields:
`defaultTimeoutSeconds` and `timeoutSeconds`. The fixture matches the
CRDs — applying the issue's verbatim YAML against the live cluster
would fail OpenAPI validation. Same with the `Sandbox`: `resources` is
a required field in the spec (not optional), so the fixture mirrors
the template's defaults to satisfy the schema while still being a
no-op for Plan 02's fake adapter.

### `kubectl wait --for=jsonpath`

The jsonpath form lets us assert on a CR's custom status field
(`status.phase`) without writing a polling loop. It was added in
kubectl 1.30 and is stable in 1.31 (our pinned `KIND_NODE_IMAGE`).
This is what the issue called out as the kubectl-version contract;
keeping it explicit in the script header so the next person who
tries to bump kind down a minor knows what breaks.

### `set -euo pipefail`

Standard hardening: any unset variable, failed pipe stage, or
non-zero exit short-circuits the script. Without it, a malformed
`kubectl wait` invocation could silently print "smoke: controller
reconciled..." and exit 0, which is the worst possible failure mode
for a CI gate.

## Validation

- `just fmt` ✅ (workspace formatting unchanged).
- `cargo clippy --workspace --all-targets -- -D warnings` ✅
  (no Rust files touched; clippy run for completeness).
- `just test` ✅ (no Rust files touched; tests run for completeness).
- **End-to-end happy path:** `just cluster-up && just smoke`
  on the dev box exited 0:
  ```
  smoke: waiting for sandbawks-controller deployment to become Available
  deployment.apps/sandbawks-controller condition met
  smoke: applying .../deploy/kind/fixtures/sandbox-smoke.yaml
  sandboxtemplate.sandbawks.io/smoke-template created
  sandbox.sandbawks.io/sbx-smoke created
  smoke: waiting for sandbox/sbx-smoke to reach phase=Running
  sandbox.sandbawks.io/sbx-smoke condition met
  smoke: controller reconciled sbx-smoke to Running
  ```
- **End-to-end failure path:** scaled
  `deploy/sandbawks-controller` to 0 replicas, re-ran `bash
  scripts/smoke-assert.sh`. The script reached the phase-wait step
  and exited 1 with a readable diagnostic
  (`error: timed out waiting for the condition on sandboxes/sbx-smoke`).
  Note: a deployment with 0 replicas is still reported as `Available`
  by kube — that's expected behaviour, and the meaningful assertion
  for "is the controller doing its job" is the *phase* wait that
  follows.

## Out of scope (deferred)

- Full state-machine path assertions (`Running` → `Pausing` → `Paused`
  → `Resuming` → `Running`). The fake adapter supports them; this
  task only covers the happy `Creating` → `Running` transition the
  parent epic calls for. A `Plan 02.5` follow-up can extend the
  assertion if needed.
- Wiring `just smoke` into the Forgejo Actions workflow — that's the
  next ticket in the epic (T7+), which lands the actual CI job that
  chains `cluster-up` → `smoke` → `cluster-down`.
