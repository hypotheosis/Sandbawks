# Plan 03 T5 — envd PTY service implementation

Date: 2026-05-23

Issue: #58
Epic: #53 — Plan 03 envd-rs

## What landed

Replaced the empty `crates/envd/src/pty.rs` stub from T1 with a working
PTY layer that plugs into the existing `Process` service. The upstream
E2B `process.proto` does not define a separate PTY service — instead,
the existing `Process` RPCs grow PTY behavior whenever `StartRequest`
sets the optional `pty` field. The four logical PTY operations from the
issue map to existing RPCs:

| Issue method | Existing RPC |
|---|---|
| `Create(cmd, args, env, cwd, rows, cols)` | `Start` with `pty: Some(PTY{size})` |
| `Stream(id)` | `Start` / `Connect` (server stream) + `SendInput` / `StreamInput` (client → server) |
| `Resize(id, rows, cols)` | `Update` with new `pty.size` |
| `Kill(id, signal)` | `SendSignal` (unchanged) |

## Modules

- **`crates/envd/src/pty.rs`** — new building blocks used by
  `process.rs`:
  - `open(rows, cols) -> (master, slave)` — `nix::pty::openpty`
    wrapper.
  - `PtyHandle` — `tokio::io::unix::AsyncFd<OwnedFd>` wrapper
    that flips the master to `O_NONBLOCK`, exposes async `read` /
    `write_all`, and a `TIOCSWINSZ`-based `resize`. Maps `EIO` on the
    master to EOF (`Ok(0)`), which is the kernel's signal that the
    slave side has been fully closed (child exited).
  - `install_controlling_tty()` — `pre_exec` callback. `setsid()` to
    become a fresh session leader, then `ioctl(0, TIOCSCTTY, 0)` to
    acquire the slave (already inherited as fd 0 by the spawn
    machinery) as the controlling terminal.

- **`crates/envd/src/process.rs`** — `spawn_child` now dispatches on
  whether `req.pty.is_some()`. The non-PTY path (renamed to
  `spawn_pipe_child`) is untouched; the new `spawn_pty_child`:
  1. Allocates the PTY with the initial winsize.
  2. `OwnedFd::try_clone`s the slave three times, hands them to
     `Command::stdin/stdout/stderr` via `Stdio::from(_)` so the spawn
     machinery dup2's each onto fd 0/1/2 in the child.
  3. Installs the controlling-tty pre-exec callback.
  4. Wraps the master in `PtyHandle`, registers it on `ProcessEntry`
     under a new `pty_master: Option<Arc<PtyHandle>>` field.
  5. Spawns a reader task that emits `DataOutput::Pty(bytes)` events
     onto the broadcast channel, and an input-forwarder task that
     drains the entry's `stdin_tx` mpsc and writes to the master.
  6. The wait task awaits the reader handle *before* publishing the
     `EndEvent`, same drain-before-end invariant as the pipe path.

  `SendInput` and `StreamInput` route via a new `classify_input` helper
  that pairs the entry's I/O backing against the proto's input oneof:
  pipe-backed processes accept only `Stdin`; PTY-backed processes
  accept only `Pty`. Mixing returns `FAILED_PRECONDITION` rather than
  silently dropping data.

  `Update` was previously a no-op placeholder; it now honors the
  `pty.size` field and invokes `PtyHandle::resize` (which is just
  `TIOCSWINSZ` under the hood). The child receives `SIGWINCH` from the
  kernel as a side effect.

## Tests

`crates/envd/tests/pty.rs` (gated on `target_os = "linux"`):

- `bash_prompt_echoes` — spawns `bash --noprofile --norc -i`, sends
  `echo $((40 + 2))\n` via `SendInput::Pty`, observes `42` in the PTY
  output stream within 5 s. Cleans up with `SIGKILL`.
- `resize_succeeds` — starts `bash -c "sleep 0.5; stty size"` at 1×1,
  immediately issues `Update` with size 24×80; the half-second sleep
  guarantees the resize lands before `stty` queries the kernel.
  Asserts `24 80` appears in the PTY output.
- `kill_with_sigterm_exits` — spawns `sleep 60` with a PTY, sends
  `SIGTERM`, asserts `EndEvent` within 3 s.
- `multiple_inputs_serialize_in_order` — runs `cat` under a PTY, sends
  `a\n`, `b\n`, `c\n` in rapid succession, asserts the first
  occurrences of `a`/`b`/`c` in the master output stream are strictly
  ordered. Cleans up with Ctrl-D (0x04).

The PTY tests all complete in well under a second on a developer
machine; combined runtime of the file is ~0.5 s.

## Design notes

- **No separate registry**: the issue's "Registry mirrors T4's Process
  registry (`Arc<DashMap<u64, PtyEntry>>`)" sketch describes the shape
  of what was needed. The actual implementation reuses T4's
  `Arc<Mutex<HashMap<u32, Arc<ProcessEntry>>>>` registry and adds an
  optional `pty_master` field — same pid keying, same retention
  semantics, no second lock to manage and no second list to dedupe for
  `List`.
- **One reader, not two**: pipe-backed processes have separate
  stdout/stderr reader tasks because the kernel hands them as two pipes
  to the parent. PTY-backed processes have a single reader on the
  master, since the slave merges all three streams (and the kernel's
  line-discipline echo) into one bidirectional channel.
- **`EIO` → EOF**: on Linux, reading from a PTY master returns `EIO`
  once all slave fds are closed. Treating it as `Ok(0)` matches the
  semantics callers expect from `read`-style I/O and avoids leaking the
  errno back through the gRPC stream.
- **`pre_exec` safety**: the callback only calls `setsid` and `ioctl`,
  both async-signal-safe. It does not allocate, lock, or read parent
  memory observably — the contract `Command::pre_exec` demands on a
  multi-threaded parent.
