# Plan 03 T7 — `envd` binary entrypoint

**Date:** 2026-05-23T18:23:13Z
**Issue:** #60
**Branch:** `feat-issue-60-envd-binary`

## Summary

Promotes `crates/envd/src/bin/envd.rs` from the T1 print-the-crate-name
stub into the real in-sandbox agent entrypoint. The binary now parses
CLI flags with `clap`, installs a `tracing-subscriber` registry,
optionally rehydrates the pause/resume snapshot via
`EnvdState::restore`, mounts the `Filesystem` and `Process` gRPC
services on the configured listen address, and drains gracefully on
SIGTERM/SIGINT with a 30 s ceiling before flushing the snapshot back
to disk.

## Files changed

- `Cargo.toml` — adds `clap = { version = "4.5", features = ["derive",
  "env"] }` to the workspace dependency table so `envd` (and any
  future binaries) can pull it from the shared version pin.
- `crates/envd/Cargo.toml` — pulls `clap`, `anyhow`, and
  `tracing-subscriber` from the workspace as runtime deps for the
  binary.
- `crates/envd/src/bin/envd.rs` — full rewrite: `Cli` struct, `main`
  → runtime → `run` split, snapshot load/flush helpers, signal-driven
  shutdown future, post-signal drain-timeout cap.
- `crates/envd/tests/binary_smoke.rs` — new integration test that
  boots the compiled binary, polls the listen port for accept, sends
  SIGTERM, and asserts exit code 0 plus a parseable snapshot file.

| `--listen <addr>` | `0.0.0.0:49983` | gRPC server bind. |

## Service wiring

Two gRPC services are mounted on the tonic `Server`:

- `filesystem.Filesystem` → `FilesystemService` (Plan 03 T3).
- `process.Process` → `ProcessService` (Plan 03 T4/T5; PTY behaviour
  is folded into Process by the upstream E2B `process.proto`, so
  there is no separate PTY service to mount).

## Shutdown sequencing

1. A dedicated tokio task installs `SIGTERM` and `SIGINT` handlers
   via `tokio::signal::unix::signal`. Whichever fires first sends a
   one-shot to the shutdown future.
2. `serve_with_shutdown` stops accepting new RPCs the moment the
   one-shot resolves; tonic then drains in-flight RPCs.
3. The serve task is wrapped in `tokio::time::timeout(30s, …)` so a
   stuck drain cannot wedge the Pod past its `terminationGracePeriod`.
4. Snapshot is flushed via `EnvdState::write_to` (atomic temp-file +
   rename) on the blocking pool.

## Snapshot lifecycle (today)

On boot, if `--state-file` exists, it is parsed and restored into
three in-binary registries (`ProcessRegistry`, `PtyRegistry`,
`WatchRegistry`). The live services still start fresh — wiring the
restored registries into them is Plan 05's job once the gVisor
adapter knows how to re-mint runtime processes. The snapshot file is
rewritten on shutdown regardless, which exercises the round-trip
path the smoke test pins.
