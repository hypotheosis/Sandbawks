# Plan 06 T2 — SDK compat CI in kind-smoke workflow

**Issue:** #184
**Parent epic:** #182
**Date:** 2026-05-26
**Branch:** `feat-issue-184-sdk-smoke-ci`

## Summary

Wires the Plan 06 T1 E2B Python SDK compatibility harness
(`tests/e2b-sdk-compat/`) into the `kind-smoke` job in
`.forgejo/workflows/kind-smoke.yaml`, so a regression in the SDK
surface blocks merges the same way the API smoke and the pause/resume
smoke already do.

## Approach

The issue's literal text asks for a new top-level Forgejo Actions job
with `needs: [pause-resume-smoke]`. The existing workflow does not
have a `pause-resume-smoke` *job* — pause/resume is a *step* inside
the `kind-smoke` job. Spinning up a separate sibling job purely for
the SDK suite would require re-creating the kind cluster, re-installing
the helm chart, and re-pulling all four workspace images (~5 min of
setup before the first pytest runs), which would push the total
runtime past the issue's "under 10 minutes" budget and conflict with
the "shares state with the pre-existing smoke" guidance from the same
issue body.

Resolved by adding the SDK suite as a **step** in the existing
`kind-smoke` job, placed immediately after the
`Pause/resume smoke (Plan 05 T14)` step. That step ordering matches
the dependency the issue articulated (SDK runs after the
gateway + snapshot path are proven healthy) without duplicating any
infrastructure work.

## Changes

### `.forgejo/workflows/kind-smoke.yaml`

* Added a new `KIND_SMOKE_INCLUDE_SDK: '1'` env entry alongside the
  pre-existing `KIND_SMOKE_INCLUDE_API` / `KIND_SMOKE_INCLUDE_PAUSE_RESUME`
  toggles. Same gate semantics: set to `'1'` to run the SDK smoke,
  anything else to skip it.
* Added three new steps after `Pause/resume smoke (Plan 05 T14)`:
  * **`Install uv (Plan 06 T2)`** —
    `uses: https://github.com/astral-sh/setup-uv@v6`. Fully qualified
    URL so Forgejo Actions does not try to resolve `astral-sh/setup-uv`
    against `data.forgejo.org` and 404 (per the auto-memory note about
    Forgejo Actions `uses:` URLs).
  * **`SDK compat smoke (Plan 06 T2)`** — opens its own
    `kubectl port-forward svc/sandbawks-api 8080:8080` (scoped to the
    step so it doesn't collide with the API smoke's or pause/resume
    smoke's port-forwards, which are already torn down by their EXIT
    traps), then runs
    `just sdk-smoke --junitxml="${GITHUB_WORKSPACE}/sdk-smoke-results.xml"`.
  * **`Upload SDK smoke junit results`** —
    `uses: https://github.com/actions/upload-artifact@v4`. Runs on
    `always()` so a red test still produces the artifact, and gated
    by `env.KIND_SMOKE_INCLUDE_SDK == '1'` so the step is a no-op
    when the smoke is skipped.
* Extended the `Dump diagnostics on failure` step to also tail
  `/tmp/sdk-smoke-pf.log` and `/tmp/pause-resume-pf.log` (the latter
  was already produced by the pause/resume step but had not been
  surfaced on failure).

### `justfile`

* Changed `sdk-smoke` to a variadic recipe
  (`sdk-smoke *PYTEST_ARGS:`), forwarding `{{PYTEST_ARGS}}` to
  `uv run pytest`. Lets CI pass `--junitxml=…` without forking the
  recipe; local invocations stay identical.

### `tests/e2b-sdk-compat/README.md`

* Added a `## CI` section that describes how the harness is exercised
  in the `kind-smoke` job, names the step, points at the artifact
  upload, and explains the `KIND_SMOKE_INCLUDE_SDK` gate. Inserted
  above the existing `## Discovery-only validation` section so the
  doc still reads top-down (install → run → CI → discovery-only →
  what's covered).
